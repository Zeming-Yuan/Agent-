# 图片服务：安全切换、可恢复进度与多人隔离

规格日期：2026-11-14。本文定义待实现行为，不代表功能已实现或验收通过。

依据：已确认的对话、当前代码与现场恢复记录。用户已确认完整用户链路为最高测试 seam，随后明确要求同时支持 Windows 和 macOS，并取消个人配额相关设计。

## Problem Statement

1. 图片服务曾因可用内存低于 20GiB 被保护器主动停止。事发前后存在编辑取消、切回生图的记录，但现有证据不能确定峰值由模型驻留、卸载时序、推理工作集、缓存或其他进程中的哪一项造成。用户需要连续完成“生图→编辑→生图”，而不是通过反复重启或重提任务恢复工作。
2. 当前任务主要呈现 queued/running，运行期间进度基本固定在 10%。用户无法区分排队、卸载、加载、生成和保存，容易把数分钟冷加载当作失败。断线或工具重启后，如果无法找回原任务，重复提交会进一步延长等待。
3. 当前一个 Key 对应同一个文件库和任务库，无法区分使用者。多人需要独立凭证、文件和任务隔离，以及公平的图片调度。用户已明确取消个人配额要求，本规格不新增个人配额。
4. 用户入口同时包括 Windows 与 macOS 桌面端；仅在服务器或仅在 Mac 侧取图，不能证明两端实际可用。

## Solution

沿用现有 MCP 图片工具、HTTPS 网关、持久任务库和串行图片后端，将其形成以下完整体验：

- 每人使用独立 Key；同一人的不同设备归属同一身份。
- 提交后立即获得可恢复的任务记录；显示动态排队情况及真实执行阶段。
- 网络断开、查询超时、桌面工具重启不会自动取消图片任务；恢复后继续查询并取回同一结果。
- 切换模型前确认旧任务停止、旧模型释放，再根据目标任务的实测内存预算决定能否加载和开工。无法确认安全时等待或停止调度，并明确解释原因。
- 已接纳且具备执行条件的不同用户轮流获得图片执行机会，同一用户内部保持提交顺序。
- Windows 与 macOS 都能配置 CA 和个人 Key、调用工具、查看阶段、恢复任务、显示图片并保存结果。

## User Stories

1. 作为图片使用者，我希望连续执行生图、编辑、再生图，以便完成同一项创作而无需重启服务。
2. 作为图片使用者，我希望服务先确认内存足够再开工，以便避免任务启动后触发保护停服。
3. 作为图片使用者，我希望资源不足时知道正在等待资源，以便区分等待和服务故障。
4. 作为图片使用者，我希望看到前面还有几单，以便了解当前排队情况。
5. 作为图片使用者，我希望看到正在释放旧模型或加载新模型，以便理解切换为何耗时。
6. 作为图片使用者，我希望看到生成和保存阶段，以便知道任务实际执行到哪里。
7. 作为图片使用者，我希望只在存在可靠数据时看到百分比或步数，以便进度不会误导我。
8. 作为图片使用者，我希望网络暂时掉线后继续查询原任务，以便取回结果而不再消耗一次推理。
9. 作为图片使用者，我希望提交响应丢失后重试仍对应同一任务，以便避免重复排队。
10. 作为图片使用者，我希望明确发起的新创作可以与此前使用相同提示词，以便有意重复生成不会被错误去重。
11. 作为图片使用者，我希望桌面工具重启后能找回自己的未完成和已完成任务，以便无需记住任务编号。
12. 作为图片使用者，我希望取消操作只影响自己的目标任务，以便不会误停别人的工作。
13. 作为图片使用者，我希望在下一单开工前完成上一单的停止和清理，以便取消后不会残留后台推理。
14. 作为图片使用者，我希望知道任务失败、取消、资源等待和服务不可用的区别，以便选择继续等待、重新取图或联系维护者。
15. 作为多人服务的使用者，我希望拥有独立 Key，以便不必向其他使用者共享凭证。
16. 作为多人服务的使用者，我希望其他人无法读取、删除、引用或取消我的文件和任务，以便保护自己的素材与结果。
17. 作为多人服务的使用者，我希望不同人的相同幂等键互不影响，以便个人客户端的编号不会发生冲突。
18. 作为多人服务的使用者，我希望已进入队列的任务不会被另一人的连续提交持续插队，以便获得公平的执行机会。
19. 作为同一人的多设备使用者，我希望换用自己的另一把有效 Key 后仍能找到原任务，以便凭证轮换不会丢失数据归属。
20. 作为 Windows 使用者，我希望在实际桌面 Harness 中完成工具配置、生成、编辑和取图，以便无需依赖 Mac。
21. 作为 macOS 使用者，我希望在实际桌面 Harness 中完成同样的流程，以便两端具备一致的核心能力。
22. 作为两端的使用者，我希望中文、空格路径及自定义保存目录正常工作，以便能使用自己的素材目录。
23. 作为两端的使用者，我希望图片已生成但本地保存失败时能重试下载，以便无需重新推理。
24. 作为维护者，我希望取得关联任务和模型阶段的内存曲线，以便核对每次切换的峰值及释放情况。
25. 作为维护者，我希望未知提交结果或释放失败时停止放行下一单，以便避免孤儿任务和模型重叠。
26. 作为维护者，我希望能发放、撤销和轮换个人 Key，以便管理接入而不向使用者暴露其他人的凭证。
27. 作为维护者，我希望迁移后旧文件和任务仍有明确归属，以便数据不会被默认开放给所有新用户。
28. 作为使用者，我希望无需新增个人配额或计费机制，以便此次改造集中解决可靠性、隔离和排队体验。

## Highest Test Seam

**用户已确认：实际桌面 Harness → stdio MCP 图片工具 → HTTPS 网关 → 图片后端 → 鉴权取图 → 桌面显示与本地保存。Windows 和 macOS 分别验收。**

这是一个逻辑上的用户入口，在两个操作系统各执行一份验收。生成、编辑、恢复和取消都复用此入口，不创建另一套供验收专用的业务接口。

- 双端验收都使用真实 CA、各自配置的个人 Key、真实后端和实际图片返回；凭证通过私有渠道配置，不写入公开规格或验收报告。
- 自动回归通过现有 HTTPS 协议测试真实鉴权、任务存储、调度与文件行为，仅替换外部推理及可控故障边界。
- 内存时间序列、后端执行记录和保护器事件是同一批任务的配套运维证据；单凭桌面显示或 HTTP 成功不能证明内存安全。
- 服务器侧 stdio 测试、接口测试或人工置为 completed 的任务，都不能代替 Windows/macOS 实际桌面端验收。

## Implementation Decisions

### 1. 已查明的现状与必须保留的约束

- 当前使用 Z-Image-Turbo BF16 生图、Qwen-Image-Edit-2511 BF16 编辑；fast 编辑带 4 步 LoRA，standard/high 使用原版编辑。图片 GPU 执行串行，固定工作流，后端仅通过受控网关使用。
- 同类任务会复用缓存；生图/编辑或 fast/原版编辑 profile 切换会调用释放接口，但当前未验证该调用返回时旧模型已真正释放。
- 当前任务启动前只检查系统 MemAvailable 是否高于 20GiB，没有按任务所需内存做预算。保护器每约 2 秒检查一次，不能代替开工准入。
- CPU/GPU 使用统一内存，系统用量和 GPU 分配不可相加当作总用量。系统余量与容器内存边界均需独立核对。
- 当前任务和文件使用 SQLite 持久化；幂等映射没有用户维度；已有 queued/running/completed/failed/cancelled 状态、任务查询、定向取消及鉴权取图接口。
- 异步任务已支持 Idempotency-Key，同键不同内容返回 409；MCP 提交尚未传递此键。同步图片等待接口目前会在连接断开时取消任务，必须与新恢复语义统一。
- 既有容量边界包括全局最多 4 个未完成媒体任务、上传与生成文件合计 2GiB，以及单张图片、尺寸、参考图数量和结果大小限制。这些是现状约束，不是本次新增的个人配额。
- 当前重启会保留排队任务，并将正在执行的任务标记为失败。现有证据没有证明推理可从中间步骤恢复。
- 20GiB 余量保护继续作为最后防线；不通过降低或关闭保护器取得“通过”的结果。Spark01 聊天/视觉服务及已停用的音频能力不在本次模型改造范围内。

### 2. 任务身份、持久化与恢复

- 每个用户拥有稳定的 owner 身份；Key 映射到 owner。同一人的多把 Key 可指向同一 owner，换 Key 不改变文件和任务归属。
- 任务、上传文件、生成结果、参考图关联、幂等记录和客户端恢复记录都带 owner；由服务器从凭证推导，忽略或拒绝客户端伪造的归属字段。
- 幂等范围为 owner 与请求键的组合。相同 owner、相同键、相同业务输入返回原任务；相同键对应不同业务输入返回 409；不同 owner 的相同键互不影响。
- MCP 工具在第一次提交前持久化请求标识及恢复信息，并在重试时复用；支持传入已有请求标识，避免工具调用响应丢失后生成新标识。新的明确创作意图使用新标识，不能只按提示词或图片内容永久去重。
- 生成、编辑、同步接口和异步任务接口共享同一任务去重与归属规则。编辑重试以相同业务参数及素材内容判定，不因临时上传 ID 变化误判为新任务或冲突；素材去重只能发生在同一 owner 范围。
- 查询已有任务、重放已存在的幂等请求及下载已有结果，不要求推理后端当前在线。后端离线只能阻止创建或执行新工作，不能阻止恢复已完成结果。
- 增加当前用户的任务恢复/列举能力，支持按状态筛选及分页；MCP 暴露对应恢复入口。客户端本地记录丢失时，仍可从服务端找回自己的任务。
- 现有结果访问遵循现有文件生命周期；本次不新增自动过期删除。任务记录存在但结果已被用户删除时，明确报告结果不可用，不静默重新生成。
- 桌面恢复记录按用户身份及服务区分；Key 轮换沿用同一 owner，切换到另一人的 Key 时不得展示前一人的本地恢复列表。

### 3. 生命周期、执行阶段与异常路径

- 保留现有生命周期状态，新增正交的执行阶段。排队和资源等待保持 queued；实际处理保持 running；完成、失败、取消为终态。
- 阶段至少区分排队、等待资源、释放旧模型、加载模型、生成、保存、取消清理。中文工具输出直接解释当前阶段，不要求用户理解后端节点名称。
- 正常顺序为：接纳并持久化 → 公平排队 → 获得串行执行控制权 → 按需释放旧模型 → 验证释放并检查资源 → 加载 → 生成 → 保存结果 → 完成。资源检查未通过时进入等待资源，不提前提交推理。
- 热任务可省略实际不发生的卸载/加载阶段；fast 与原版编辑之间仍按 profile 切换处理，防止 LoRA 状态残留。
- 用户主动取消排队任务可直接进入 cancelled；运行中取消先进入取消清理阶段，确认后端任务不再运行且必要清理完成后才报告 cancelled。取消重复调用保持幂等。
- 取消、超时或失败后，只有证明后端不再持有该工作、资源状态可判断，才能放行下一单。某任务显示终态不等于后端可立即接下一单。
- 后端提交结果未知、旧任务停止失败、卸载无法确认或资源采样失效时，停止图片调度并降级健康状态。新任务返回明确的 503，不通过重提掩盖未知状态。
- 后端离线前已接纳的排队任务保留，显示阻塞原因；恢复后重新检查后端和资源，再继续调度。禁止悄悄积累新任务或无限自动重载模型。
- 网关/后端重启后保留既有任务身份、幂等记录和结果。运行中任务按既有保守恢复策略明确失败；不承诺 GPU 步骤续算。清理并确认孤儿工作停止后才恢复队列。
- 同一终态不得因迟到的后端响应改写为另一个终态；取消与完成的竞争只允许一个确定结果。错误信息包含可操作原因和关联请求/任务编号，不泄露内部凭证或其他人的内容。

### 4. 内存观测、释放确认与开工准入

- 对“生图→编辑→生图”记录完整曲线，覆盖接纳、卸载前后、加载、文本/视觉编码、采样、VAE 解码、保存和清理。至少同时记录时间、任务/owner 的非敏感标识、模型 profile、关键输入规模和阶段事件。
- 运行及切换期间以不低于每秒 5 次的频率采样系统 MemAvailable，记录容器当前/峰值用量；在后端可获得时同步记录模型驻留与分配器 allocated/reserved 等指标。采样频率不是消除瞬时峰值的保证，阶段边界还需单独打点。
- 每次切换输出最低可用内存、进程/容器峰值、旧模型释放耗时、新模型加载耗时及稳定后的基线。明确区分系统、容器和分配器口径，避免统一内存重复计数。
- 释放接口成功只表示请求被接收，不能单独作为释放完成证据。需确认上一后端任务已终止、旧 profile 不再驻留/可执行，且连续有效采样满足配置的稳定窗口。仅凭 MemAvailable 回升也不能证明旧模型释放。
- 若固定后端没有现成的可靠释放完成信号，增加最小化、只读且仅运维可见的模型生命周期观测能力；观测只服务于同一用户链路的安全判定，不新增业务工作流入口。无法给出可验证信号时，保持阻塞，不以固定 sleep 代替确认。
- 为每个启用的模型 profile 建立有证据的内存包络，涵盖尺寸、参考图数量、fast/standard/high、解码与合成等会改变工作集的因素。可用保守上界覆盖多种输入，不要求为每种组合硬编码一个数字。
- 开工判断至少满足：确认释放后的系统可用内存，能够容纳目标任务预计新增峰值、保守裕量和 20GiB 余量；容器剩余可用空间也足以容纳预计新增用量及裕量。已有驻留量与增量预算必须使用一致基线。
- 预算来自受控冷/热运行与切换测量，不从模型文件大小、历史单次最低余量或 GPU 数字猜测。模型、工作流、尺寸包络或运行时变化后重新校准；缺少有效预算的 profile 不向正常用户放行。
- 标定过程必须受控执行并保留保护器；若无安全的保守起始条件，先报告无法标定，不冒险加载。无需先证明历史事故的唯一根因才能实施新增观测和准入。
- 开工前立即复查资源；等待期间定期复查，取消仍可用。等待上限和稳定窗口配置化并在部署记录中给出有效值；超限后明确失败，不让任务无解释永久 queued，也不因等待自动新建任务。
- 保持单个图片执行/切换控制权，覆盖停止、卸载、加载、推理和清理。准入检查与实际开工之间不得由另一图片任务抢用同一预算。

### 5. 排队信息与真实进度

- 扩展现有任务查询响应，提供阶段、阶段开始时间、最近有效更新时间、等待/阻塞原因和动态 queue_ahead。原任务 ID、生命周期和结果访问契约继续使用。
- queue_ahead 表示当前公平调度快照中预计先被服务的其他图片任务数，包含正在占用执行权的任务；按实际公平顺序计算，不直接使用全库 FIFO 行号。新用户加入、取消或资源状态变化时可以调整，它不是固定承诺。
- 对外只显示数量和本人的任务信息，不泄露前方用户、提示词、素材名或任务详情。非图片媒体工作不误计为占用图片 GPU 的前方任务。
- 模型加载及保存阶段没有可靠总量时显示阶段和已等待时间，不虚构线性百分比或 ETA。存在可靠采样步数时提供当前步/总步数；这些数字只解释生成阶段，不冒充全流程完成率。
- 现有 progress 字段仅用于兼容；升级后的工具以新阶段字段和有依据的阶段进度展示，不继续把固定 10% 当作真实进度。
- 后端事件须归属正确任务并按阶段顺序处理，重连、重复、迟到事件不使终态或当前阶段倒退。事件暂时不可用时继续显示最后确认阶段及更新时间，不伪造新进度。
- 仅在图片内容完整取回、受控文件库持久保存且结果引用可读取后报告 completed。正在保存不得提前显示成功。
- MCP 查询将阶段、前方单数和阻塞原因传递给实际桌面 Harness；查询的单次等待结束只返回当前状态，不等于任务失败或取消。

### 6. 断线续取与双端客户端

- 网络断开、单次轮询超时、同步 HTTP 等待中断、MCP 进程退出均不等于用户取消；已接纳任务继续执行。只有显式取消、明确任务超时或后端失败改变其生命周期。
- 同步图片接口需要保持等待式响应，但等待超时或连接丢失后，应通过先前持久化的请求标识恢复同一任务。同步等待超时保留现有返回 task_id 的恢复方式。
- 桌面端重新连接后优先读取本地记录或当前用户任务列表，再以原任务 ID 查询；提交响应丢失时，使用原请求键重放并得到原任务。
- 生成完成后以鉴权接口下载，返回真正的 MCP 图片内容并保存到用户选择的本地目录。需 Bearer 的结果地址不能作为无需鉴权的普通图片 URL 交付。
- Windows/macOS 均提供可执行的安装或配置说明与接入包，支持平台路径、中文、空格、自定义结果目录及 CA 加载；不把 Unix shell、固定 Mac 目录或 Mac 专用命令作为 Windows 前置条件。
- 两端分别验证自己的实际 Harness 接纳 MCP 图片内容及聊天内显示；本地文件落盘成功不等同于 Harness 已显示图片。
- 本地目录不可写、磁盘满或下载中断时明确报告本地取图失败，保留已完成的服务端结果和任务标识；修复目录或网络后可重试取图，不重跑模型。
- 不提供自动化桌面软件权限或版本假设；实现时记录两端实际 Harness、版本及配置方式。未实际运行的一端必须列为未验收。

### 7. 多人隔离、凭证与公平调度

- 管理员通过受控运维入口发放、撤销、轮换个人 Key；服务器持久化可校验的凭证摘要及 owner 映射，原始 Key 仅通过私有渠道交付。日志、诊断和恢复记录不包含原始 Key。
- 所有现有受保护接口按个人 Key 鉴权；未知或撤销的 Key 返回 401。鉴权不再依赖一个供所有人共享的 Key。
- 文件读取、下载、删除、引用，任务读取、列表、取消及结果获取均检查 owner。还需覆盖同步编辑自动上传、透明前景、参考图、已有非图片媒体任务等可能绕过归属的入口。
- 对其他人的对象 ID 与不存在的对象返回一致的 404；不能借任务结果、错误信息、内容哈希去重或恢复列表探测其他人的数据。服务端内部共享后端不等于共享用户文件库。
- 图片调度采用活跃 owner 之间的轮转；每次选择该 owner 最早接纳且符合执行条件的任务。任务不抢占，正在执行的任务允许结束，随后轮到其他已有待处理任务的 owner。
- 调度顺序及轮转位置需在重启后可恢复，避免一个持续提交者借重启或时间相同不断回到队首。同一 owner 内的相对顺序稳定；队首因资源条件不能执行时保留位置并显示等待原因，可服务其他符合条件的 owner，不越过该 owner 的队首。条件解除后，在下一次可服务轮次获得机会；无 owner 可执行时等待资源变化，不循环卸载/加载尝试开工。
- 资源不足的任务不会启动；不允许以“减少模型切换”为由无限跳过另一 owner。公平性以任务轮次衡量，不保证不同模型具有相同耗时或 GPU 时间份额。
- **不新增个人任务数、存储量、每日次数、积分、计费或限流配额。** 公平调度作用于已接纳且可执行的任务，不承诺在全局队列已满时仍无限接纳新任务；此时按现有全局容量边界返回 429 和重试提示。
- 已有全局容量检查、文件保存与任务提交仍需原子执行；幂等重试不额外占一个全局任务位置。暂存清理、失败及取消不能删除其他 owner 正在使用的素材。

### 8. 迁移与上线顺序

- 上线前备份文件库、任务库和鉴权配置，记录可回滚边界；先迁移 owner 与幂等索引，再启用多 Key，不能出现半迁移期间跨用户可见的窗口。
- 旧文件和任务归入明确的 legacy owner，由维护者指定接管身份；不能复制给每个新用户或默认公开。旧共享 Key 只能映射到明确 owner，不再作为多人通用回退凭证。
- 保留旧任务 ID、结果引用和可恢复关系。迁移须能安全重试；运行中任务按保守策略收敛，不自动重放推理。
- 先完成隔离与故障回归、真实后端内存标定，再做受控切换试验及 Windows/macOS 用户链路验收。标定和客户端验收未完成时，不宣称对应功能可交付。
- 记录有效资源预算、稳定窗口、等待上限、已启用 profile、全局容量边界和客户端兼容配置；保留操作与恢复说明，不扩大为新管理后台。

## Testing Decisions

1. 好测试通过用户或外部可见行为判断：任务身份、HTTP/MCP 输出、授权后的文件内容、执行顺序、真实图片和资源证据；不依赖私有函数调用次数、固定等待 sleep 或某张内部表的实现形状。
2. 主验收从已确认的 Windows/macOS 桌面链路分别执行：配置个人身份、生成、参考图编辑、再生成、显示阶段、显式取消、断线恢复、结果显示与保存。测试时登记实际平台、Harness 及版本。
3. 集成测试运行真实网关、鉴权、持久存储、图片 worker 和调度；借外部后端替身控制慢加载、采样、保存、取消、提交响应丢失及资源信号。以真实 HTTP/MCP 结果及后端实际接收的工作为判据。
4. 复用已有测试先例：网关持久任务与幂等测试、重启保留排队任务测试、图片后端离线拒绝建单测试、定向取消后下一单完成测试、提交结果未知时停止放行测试、编辑重试复用任务测试，以及 MCP 返回真实图片内容和本地文件的桥接测试。
5. 新增多身份矩阵：A/B 上传相同或不同素材，互相读取、删除、引用、取消、列表与取图全部被隔离；同键请求不跨人冲突，同一人的轮换 Key 可恢复原任务，撤销 Key 不能继续访问。
6. 从客户端提交入口覆盖提交前断线、服务端接纳但响应丢失、生成中断网、保存中断网、取图中断网、MCP 重启和重复工具调用；同一请求只出现一次后端推理，显式新请求仍可重新生成。
7. 同步与异步接口均覆盖断线不自动取消、超时可恢复，以及后端已离线时仍可读取已有任务/结果或返回已有幂等任务。引用已删除结果应明确不可用。
8. 公平调度使用多个有持续任务的身份，在不超过现有全局容量的条件下验证轮转、用户内顺序、取消、重启后的顺序，以及新请求不能持续插队。另测全局满载明确拒绝；不把“可无限接单”设为验收条件。
9. 资源故障注入覆盖预算不足、采样不可用、释放仅返回成功但尚未完成、旧推理未停止、容器余量不足及预算失效；断言不会向后端启动不安全的新工作，且用户能看到明确状态或错误。
10. 内存安全必须在真实图片节点验证：对每个拟启用的编辑 profile，至少完成三轮“生图→编辑→生图”，包含冷/热状态、代表性最大支持输入包络和一次编辑取消后回切。每轮保留连续曲线、释放/加载边界、任务结果与容器峰值。
11. 内存包络覆盖 fast、standard、high 时分别给出依据；未完成真实标定的 profile 保持不放行，不能用纯工作流断言替代硬件验证。若要宣称全部现有模式可用，必须完成全部对应标定。
12. 真实内存验收要求所有受测任务符合有效预算、系统最低余量不低于 20GiB、未触发保护停服、没有已证实的旧/新模型不安全重叠；资源不足场景通过安全等待/拒绝验收，不能靠强行执行通过。
13. 迁移使用真实旧格式数据副本覆盖既有文件、排队/运行/完成任务、相同幂等键、迁移中断和重试；通过接口确认归属正确且结果仍可取，备份能恢复。
14. 进度验收记录阶段序列、queue_ahead、更新时间与实际事件相符；验证无可靠进度时不展示虚假百分比、不会提前显示成功、迟到事件不能覆盖终态。实际取图失败只需重试下载。
15. 规格交付本身只核对内容与发布结果；上述实现和硬件测试由后续实现任务执行，不能将既有回归记录冒充本次改造的验证结果。

## Acceptance Criteria

以下全部满足才可把本规格对应的实现标为完成；仅发布规格不代表这些条件已通过。

| 编号 | 可观察验收条件 |
| --- | --- |
| AC-01 | Windows 与 macOS 各自从实际桌面 Harness 完成生成、编辑、再生成，收到并显示真实 MCP 图片，图片保存到指定本地目录。 |
| AC-02 | 每个启用编辑 profile 至少三轮切换实验具有完整内存曲线、阶段事件与结果；覆盖冷/热、支持输入包络及取消回切。 |
| AC-03 | 所有真实内存验收运行符合已标定预算及容器边界，MemAvailable 不低于 20GiB，未触发内存保护停服；保护器保持启用。 |
| AC-04 | 旧推理未停止、旧 profile 未确认释放、预算不足或资源信号无效时，不启动新模型/新推理；任务显示资源等待或明确故障。 |
| AC-05 | 释放完成证据不只依赖释放 HTTP 返回、固定 sleep 或单次内存回升；能关联到目标旧 profile 和对应切换任务。 |
| AC-06 | 桌面可见动态前方单数及排队、资源等待、卸载、加载、生成、保存、取消清理阶段；无可靠数据时不伪造百分比或 ETA。 |
| AC-07 | 同一请求在响应丢失、网络恢复和 MCP 重启后仍找回同一任务，后端只执行一次；有意发起的新请求不被错误合并。 |
| AC-08 | 同步、异步接口及工具查询断线不会自动取消已接纳任务；同步等待超时能继续按原任务或请求标识恢复。 |
| AC-09 | 本地恢复记录丢失后可列出本人任务找回结果；后端离线时仍可读取已有记录、重放已有幂等任务并下载已保存结果。 |
| AC-10 | 本地目录不可写或下载中断后，修复条件即可重新取图，不创建新推理；服务端结果已删除则明确报不可用。 |
| AC-11 | 两名用户拥有不同 Key；跨人文件读/删/引用、任务查询/取消、恢复列表及结果读取均返回一致不可见结果，不暴露元数据。 |
| AC-12 | 同人 Key 轮换保留 owner 和数据访问；撤销或未知 Key 返回 401；日志与发布材料无原始 Key。 |
| AC-13 | 不同用户使用同一幂等键互不冲突；同人同键同业务输入返回原任务，同人同键不同输入返回 409。 |
| AC-14 | 已接纳且可执行的活跃用户按轮次获得图片执行机会，用户内顺序稳定；连续提交、取消或重启不能造成其他用户持续饥饿。 |
| AC-15 | 全局容量达到现有边界时按既有规则拒绝新工作，返回明确状态和重试提示；不新增任何个人配额或计费限流。 |
| AC-16 | 显式取消仅影响目标任务；确认后端停止和必要清理后才报告取消完成并放行下一任务，完成/取消竞争保持唯一终态。 |
| AC-17 | 提交结果未知、卸载失败或后端不可用时健康状态正确降级，新建工作明确 503；已接纳任务不悄悄丢失、不自动重复提交。 |
| AC-18 | 资源等待具有部署记录中明确的上限与复查规则；超限明确失败且可诊断，不永久无解释排队。 |
| AC-19 | 旧数据迁移后归入明确 legacy owner，原任务与文件引用有效；其他新用户默认无权访问，迁移可重试且有恢复备份。 |
| AC-20 | 现有生成参数、编辑模式、透明前景合成、标题、媒体文件限制及主聊天链路不因本次修改意外退化；未验收平台或 profile 如实列出。 |

## Out of Scope

- 个人任务数/存储量/次数配额、积分、计费、个人限流，以及相关面板或通知。
- 公网开放注册、SSO、团队协作共享、文件分享链接、完整用户管理后台。
- 多 GPU 并行图片推理、抢占正在运行的任务、按 GPU 秒数计费或公平分摊、分布式调度。
- 按模型亲和性无限延后其他用户、保证新任务总能进入已满队列，或承诺固定排队时长/冷启动 SLA。
- GPU 推理断点续算、崩溃后无条件重跑、关闭保护器后的强制加载，以及无人值守的无限恢复重启循环。
- 更换生图/编辑模型、提升画质或与外部产品画质对标；扩展任意工作流、远程 URL、mask、额外图片尺寸或批量并行能力。
- 恢复停用的音频能力、重做聊天/视觉模型、聊天调度公平性，以及新增独立网页或手机客户端。
- 对所有桌面 Harness 和所有 Windows/macOS 历史版本的兼容保证；本次按实际登记的双端环境验收。
- 追溯性断言历史故障的唯一根因或把本次功能验收等同于完整 8 小时业务稳定性验收。

## Further Notes

### 假设与真正未决问题

1. **已确认的范围修正**：不做个人配额；Windows 与 macOS 同等纳入；最高测试 seam 是双端实际用户链路。无需重新访谈这些事项。
2. **调度假设**：采用不抢占的按 owner 轮转，公平性针对已接纳、具备资源条件的任务。全局 4 单已满时，新用户也可能收到 429；本规格不新增预留名额或个人上限来解决接纳竞争。
3. **尚待实测**：历史内存峰值的具体来源、不同 profile 的可靠增量预算、裕量与释放稳定窗口。它们是实施期间的观测/标定交付项，不是可凭空填写的已知数字；未标定即不放行相应 profile。
4. **配置待登记**：资源等待上限与稳定窗口的最终有效值，需要依据标定、现有推理超时和实际运行记录确定并写入部署配置。运行超时只从实际执行计算，排队/资源等待单独计时。
5. **环境待登记**：两端实际 Harness 名称、版本、Windows/macOS 版本和安装方式。当前有跨平台 Python 桥接基础和 Mac 包，但不能据此声称已具备 Windows 安装验收或双端一致展示。
6. **迁移待指定**：已有共享数据的 legacy owner 接管身份，以及个人 Key 的实际发放名单。实现可通过测试身份和迁移副本推进；生产多用户启用前须由维护者明确映射。
7. **已有边界**：本轮未要求改变全局队列和存储安全边界；本规格不把这些既有全局边界扩展为个人配额。

### 事实与证据来源

- 当前网关鉴权、任务/文件持久化、图片 worker、同步图片路由和 MCP 图片桥接实现。
- 《生图和图片编辑接口》及《OPERATIONS》中的图片服务、fast 编辑与 2026-11-14 队列恢复记录。
- 2026-11-14 14:42:48 保护器记录 MemAvailable=20387564KiB 后主动停止图片服务；该事件不能直接解释为内核 OOM。

- 现有回归、服务器侧 stdio 样例和一次恢复后的最低内存记录，仅说明当时场景，不证明本规格新增的连续切换、双端恢复和多人隔离已经通过。
